# 任务规则

任务由题面、数据、评测器和参考提交组成，不写完整的求解流程。
下面每个条目都是必须满足的要求；审查时，问题按条目名归类。

## core_problem_alignment
任务围绕论文的核心科研问题，覆盖其中可通过计算完成、能够复现并客观评测的研究工作。

任务的提交产物和评分必须能够评价求解者对核心科研问题的解决程度。不能仅选择容易实现的子实验、辅助分析或下游验证，就把它当作整个科研问题。

任务允许求解者采用任何合理方法，不要求采用论文指定的算法或复现作者的完整处理流程；不要求完成湿实验。方法自由不意味着可以缩减能够复现的实验和评测范围。

## experiment_coverage
先完整清点论文中的实验和评测，再确定任务内容。

- 核对正文、补充材料、图表及对应代码中的实验，说明各实验验证什么科学问题，使用什么数据和实验条件，通过哪些手段评价结果。
- 能够复现并客观评测的实验及评测手段应尽量全部纳入。
- 同一指标在不同数据集、实验条件或对象上的评价应分别核对，不能因为指标同名就遗漏其中一部分。
- 确实无法复现或客观评测的项目可以排除，但必须在计划中注明原文位置、具体原因和证据。尚未检查不能当作无法复现；实现麻烦、被认为次要或一次运行失败不能作为排除依据。
- 计划必须说明已纳入和未纳入的实验及评测手段。记录方式不限，不要求额外文件或固定 JSON 结构。
- Writer 必须落实已纳入的实验和评测要求，不能自行缩减范围。
- Reviewer 必须独立对照论文检查遗漏及排除依据，不能只检查计划中已经选择的内容。
- Repair 应补齐遗漏或提供可核实的排除依据，不能通过删除难以通过的实验或指标获取通过结论。

## task_package
最终成品采用 Harbor 任务包结构，包含 environment/Dockerfile 和 tests/Dockerfile，沿用对应领域现有的实验环境和评测环境。

草稿中的求解者输入放在 data/，打包时放入 environment/data/。实验 Dockerfile 可以由打包程序根据共享环境生成；草稿必须提供 tests/Dockerfile，使评测所需文件和入口能在评测环境中就绪。

tests/ 除 Dockerfile 外，不规定其他文件名、目录层级、编程语言或文件格式；具体组织方式由实际评测需要决定。

tests/ 只包含评分实际需要的程序、依赖和数据。不得默认复制整份求解者输入。需要独立执行提交算法、计算指标或核验结果时，可以提供必要的输入或评测数据，并说明用途。

Dockerfile 必须使评测环境具备可运行的评测入口和所需文件。隐藏参考与答案不得进入求解者环境。Harbor 的 Linux 评测入口是容器内 /tests/test.sh；可以在构建时生成或由其他名称的源文件复制得到，不要求源目录存在同名脚本。

## scientifically_grounded
有真实科学依据且有意义——源自真实科研工作流。

任务必须来自输入的科学论文，即实际研究者会构建、运行、调试或解决的计算工作，例如数据分析流水线、模拟设置、数值求解器、模型拟合、仪器数据处理、图像或信号处理。数据优先使用输入的真实数据；材料不完整时，允许使用有科学依据的公开真实数据替代，并说明来源和替代理由。

评判代理实际做的工作，而不是任务主题。使用蛋白质、光谱、基因组、望远镜等科学术语，不能把通用编码、数据格式转换或现成的机器学习/统计拟合变成科学任务。

请检查：研究者是否真的会执行这一具体步骤；是否能指出真实的论文、数据集、流水线或项目，其中确实发生了这项工作；结果是否具有现实科学价值，至少有某个真实受众会关心。

任务必须是研究级工作，而不是大学课程项目、教材练习或“学习某种技术”的训练题。任务不能是噱头、脑筋急转弯，也不能只是因为冷僻而显得困难。

## source_anonymization
instruction.md 不泄露输入来源或原始答案来源。

instruction.md、task.toml、README.md 以及其他交付文件不得出现输入论文的名称、作者、期刊、DOI、引用信息、原论文代码仓库或输入路径。
完成任务所必需的科学概念、数据集名称和数据来源说明可以保留，但不得让代理仅通过查看任务元数据定位原始论文、原始代码或隐藏答案。

## data_split
任务 data/ 只包含求解者做题必需的原始数据。

- 分工：Planner 在计划中给出划分建议；Writer 按建议把求解者数据复制、改名、拆分或做无损格式转换后放进草稿draft/data/，Repair 可以继续修改；Reviewer 审核最终 data/。成品公共数据由草稿 data/ 打包到 environment/data/，程序不另外挑选或补充来源数据。
- 计划的 data_split.files 为来源数据目录下每个文件或目录标注 path、role、reason，role 取值：
  - solver_input：原始观测数据或公开注释，求解者做题必需；
  - author_result：原研究或数据提供方对这些数据算出的分析结果，例如关联统计、耦合或相关系数表、显著性列表、聚类或分群标签、模型预测、处理后的矩阵、补充表格；
  - evaluation_reference：评测要用到的评测数据、真值、标签或参考集合。
- 任务 data/ 只能包含 solver_input 的内容，或由 solver_input 无损转换、拆分、抽样得到的文件；不得包含 author_result 与 evaluation_reference，也不得包含由它们生成的文件。程序会拦下与这两类来源文件字节相同的文件。
- 同一份数据只放一份；文件名和目录结构使用中性命名，不保留暴露来源论文、实验设计或答案的路径与文件名（例如来源仓库的目录层级、样本分组标签）。
- 内容由原研究方法计算得出的文件一律算 author_result，即使它来自官方镜像或教程、文件名看起来像原始数据。
- 求解者不做核心分析、只对某个文件做排序或过滤，就能直接或近似得到评分所比较的结果，这个文件就不得是 solver_input。
- author_result 与 evaluation_reference 只能用于 tests/ 和 solution/；instruction.md 不得把它们当作输入或“辅助资料”介绍。
- 评分需要“未参与拟合的样本”时，由造题方固定划分评估集，写明划分规则和随机种子；评估集的真值只放在 tests/，不得出现在 data/。

## verifiable
验证器可靠、确定且高效，并能核验具体、可检查的科学结果。

verifier 至少应检查提交物是否存在且符合输出 schema、各计分指标的取值，以及结果是否明显伪造或为空操作。不能只检查文件存在、脚本退出码或固定文本。
验证器应高效、可靠、确定；即使重复运行数百次，也不应因验证器自身不稳定而失败。对于包含随机性或其他非确定性的任务，验证器必须显式、正确地处理非确定性。不接受仅要求假设生成、文献综述或其他无法可靠判定对错的开放式任务。

## metric_provenance
计分指标、数据与参考科学结果均有原文评估依据，允许本条规定的准确性误差转换。

- 按实验提取原文使用的评测手段，尽量保留所有能够复现的评价维度，包括结果准确性、稳定性、鲁棒性、跨数据集表现及效率等。
- 每种评测手段都应核对科学量定义、数据条件、统计口径、原文参考结果及对应代码；不能只保留最容易实现的一项。
- 保留原文已有指标，不能用一个方便计算的误差指标代替原文多种不同的评价。准确性误差转换仍须遵守本条原有条件。
- 评测方法应能公平评价不同的合理解法。对照算法或作者特定结构不能直接变成求解者必须采用的方法；无法适用于其他合理解法的评价，应说明具体原因。
- 计分指标的科学定义须有原文评估依据。数据和参考数值优先使用论文及给定材料；材料不完整时，允许使用有科学依据的替代数据，或依据作者代码、原文公式重新计算参考数值，并在计划中说明来源、数据条件和计算依据。除下述准确性误差转换外，不得加入原文评估部分不存在的计分指标。
- 每个指标写 name、source、definition、paper_value、paper_interval、dataset、code_ref、experiment、direction、starter、bound、sota：（plan的格式尽量按这个写，但是reviewer不要对plan.json的格式细究）
  - experiment：所属实验的 name；
  - direction：higher（越大越好）或 lower（越小越好）；
  - starter：空提交时该指标的取值；空提交下算不出的，取“什么都不做”对应的值（例如检出率 0、R² 0），并写依据；本条新增的准确性误差转换按下表使用有依据的简单基线误差；
  - bound：理论上界（higher）或理论下界（lower），没有时写 null；
  - sota：按 scoring 条目由 paper_value、starter、bound 算出，写出计算过程；不得用参考提交的得分反推。
- 一般只有单调指标参与计分。但是当任务要求准确估计、预测或重建一个科学结果时，允许以提交结果与原文参考结果的绝对误差作为计分指标，误差越小越好。同类对象有多个时，可以使用平均绝对误差。
- 比较双方必须具有一致的对象、数据条件、单位和统计口径。原文参考结果及其出处沿用本条现有要求记录。格式、文件数量等完整性要求不能包装成误差指标参与计分。
- 原文已经使用 MAE、RMSE 等误差指标的情况，继续沿用原文定义和数值，不重复转换。
- 格式、完整性和防作弊检查不属于计分指标，但必须在计划或评测实现的说明中写明它们相对原文评估新增了什么。

对于“与参考结果比较”误差指标，可以参考：

| 字段 | 含义 |
|---|---|
| definition | 写明原始参考值 r 和误差公式，例如 e = abs(r̂ − r)；多个同类对象可取平均绝对误差 |
| direction | lower |
| paper_value | 0，表示与参考结果完全一致时的误差；原始参考值 r 写在 definition 中 |
| paper_interval | null；原始参考结果的区间在 definition 中说明 |
| bound | 0 |
| starter | 有依据的简单基线产生的误差，必须有限且大于零，并说明基线及计算依据 |
| sota | 按原公式计算，结果为 0 |

没有合理基线时，应重新设计该指标，不能随意指定一个数。

## scoring
评分为 0–1 的连续总分。

1. 单个指标得分，x 为提交算出的指标值：
   - higher：sota = min(paper_value + 0.5 × (paper_value − starter), bound)
     x ≤ starter → 0；starter < x ≤ sota → (x − starter) / (sota − starter)；x > sota → 1
   - lower：sota = max(paper_value − 0.5 × (starter − paper_value), bound)
     x ≥ starter → 0；sota ≤ x < starter → (starter − x) / (starter − sota)；x < sota → 1
   - bound 为 null 时，上式中的 min / max 只取前一项；
   - sota 与 starter 相等时：x 优于 starter 记 1，否则记 0；
   - 指标无法计算（缺文件、格式错误、NaN）→ 0。
2. 每个实验的得分 = 该实验全部计分指标得分的最小值。
3. 总分 = 全部实验得分的最小值，等价于全部计分指标得分的最小值。
4. 允许将格式、输出覆盖、数值边界、输入完整性和提交自报值一致性作为硬性检查；这些检查任一不通过时，总分可以为 0。除此之外的防作弊检查必须有论文、原始代码或客观数学事实作为依据；没有可审计依据的检查不得进入 verifier，不能通过审查，也不能用于清零。

对于 metric_provenance 允许的新准确性误差指标，令 x 为提交误差，paper_value = 0、bound = 0、starter > 0，则原 lower 公式得到 sota = max(−0.5 × starter, 0) = 0，得分 = max(0, 1 − 提交误差 / 基线误差)。完全准确得 1 分，误差越大分数越低，达到或超过基线误差得 0 分；缺文件、无法计算或无效数值直接得 0 分。

## test_code_provenance
verifier 的指标计算出自原论文代码，没有对应实现时与原文公式等价；允许下述准确性误差转换。

计划中给出 code_ref 的指标，tests 的实现必须与 code/ 中对应函数等价：公式、归一化、聚合方式、过滤条件和数据子集一致，可以移植或改写但不能改变计算结果。
采用替代数据时，说明必要的数据适配，保持指标定义和统计口径一致。
code_ref 为 none 的指标，必须先确认 code/ 中确实不存在相应的评估实现，再按原文公式实现。
本规则允许的准确性误差转换可以由评测器新增实现，不要求原论文仓库已有对应误差函数；被比较的科学量仍须遵守原文口径。
计划中按实验列出计分指标，逐个指标写明原文出处、原文数值、code_ref、direction、starter、bound、sota 及依据，以及 tests 相对原文评估的全部改动。

## well_specified
指令完整、简洁且无歧义地说明要提交什么、考察什么。

instruction.md 必须写出背景、输入数据、任务、提交产物、评测方式和资源限制，并允许代理采用任意合理方法完成任务。涉及文件时应使用运行时可访问的绝对路径。
instruction.md 必须直接从科学背景开始，不得在开头添加题目名称、任务名称或以题目名称为内容的标题；可使用“科学背景”作为首节标题。
instruction.md 要写成一道独立的科研挑战题，而不是对论文的复述：只说明给什么数据、要得到什么结果、考察哪些科学指标。
instruction.md 中不能出现解决该问题的方法提示或机器学习相关方法，也不能描述原研究如何使用数据：选用了哪些列或标签、过滤阈值、归一化或预处理方式、参数取值，以及原研究在该数据上得到的数量结果（如过滤后的基因数、聚类数、每个位置的细胞数）。描述数据本身（文件格式、各字段含义、样本对应关系）是允许的。若某个选择决定了输出结构（例如输出列取自哪一套标签），写成对输出的要求，而不是处理步骤。
评测方式一节只列科学指标及其计算口径；不写 starter、sota、阈值、权重或计分方式，也不写指标计算用到的具体基因名、位点或参考集合内容。输出格式只在“提交产物”一节说明。
如果把指令交给一位无法联系作者的独立领域专家，对方仍能完成任务，则指令定义充分。
所有必需信息必须明确写在指令中，或属于该领域的标准知识。不得依赖作者私下掌握的信息、未公开的默认值或无法访问的上下文。

## solvable
存在参考答案，参考提交可以拿到分数。

必须存在参考答案；参考提交（solution/solve.sh）在任务环境中运行后，verifier 给出的总分必须大于 0 且不超过 1；不要求满分。
若任务只能通过复现作者的隐藏实现、读取泄漏答案或依赖不可用资源完成，则判定为 FAIL。

## reference_submission
参考提交优先迁移自论文仓库；采用替代数据时，允许依据原文方法进行必要适配，并说明依据。

- solution/solve.sh 优先把论文代码仓库中的参考结果或参考代码迁移过来，在任务环境中把结果写到 instruction.md 规定的提交路径；
- 只能读取 solution/ 和任务 data/，不得读取 tests/，不得联网；
- 不审查参考提交用的方法；输出路径和格式必须与 instruction.md 一致；
- 辅助代码超过约 20 行时，放在 solution/ 下的独立文件中，而不是作为大型 here-doc 嵌入 solve.sh。

## outcome_verified
测试评判结果而非过程——指令描述终态，不规定步骤。

评分必须基于最终结果，而不是代理采用的具体方法。例如，不能要求必须用 Emacs 编辑文件并排斥 Vim。

可以要求特定输出格式，但要求应简单、清楚，并服务于结果验证。任务指令应描述终态，不应把无关的实现步骤当作硬性要求。

## essential_difficulty
难度来自科学推理与领域知识，而非格式细节或任意精度。

核心难度应来自科学推理、领域知识、方法选择、多步问题求解、真实的技术调试或工作流复杂性，而不是输出格式必须完全一致、任意数值精度、单位或坐标惯例等文书细节。

收窄计分区间不能凭空增加科学难度。若区间收窄到只有参考流水线能得分，测量的是与参考实现的一致程度，而不是更多科学知识。应问：提交必须在科学上正确处理什么才能改变统计量或最终结果；采用不同但正确的方法是否仍能得分；正确方法与缺陷方法的结果是否有明显、合理的间隔。

若难度来自真实科学或技术挑战，判定为 PASS。若大部分失分会因格式边缘情况、输出精度或文书细节造成，或区间窄到只有参考实现可靠得分，判定为 FAIL。

## anti_cheat_robustness


验证器直接使用的参考值和答案文件不得通过镜像构建、文件复制等方式进入 Agent 可见环境或 data/。

代理以 root 身份运行并拥有完整系统访问权限，因此必须按实际容器内容评估泄漏风险。答案不得嵌入环境文件或 Docker 镜像层，也不得通过简单查看文件取得。测试不得依赖可变外部资源，使代理能够借此走捷径。

判断泄漏风险时，应以代理容器实际可访问的路径为准：environment/Dockerfile 复制进去的内容属于代理可见内容；代理文件系统在构建或运行时写入的内容属于代理可见内容；solution/ 不会复制到代理镜像，因此其中的参考结果不构成泄漏。

## task_security
任务不包含恶意代码、凭据外传或针对代理、主机的攻击。

成品任务必须包含可运行的 task.toml、instruction.md、README.md、实验和评测 Dockerfile，以及验证任务所需的其他文件；草稿与打包程序的分工遵循 task_package。
所有任务文件，包括题面、参考提交、评测入口及其实现文件、辅助脚本和数据，都必须安全。任务会让代理以 root 权限在容器内运行，评审者或贡献者也可能在自己的机器上运行任务。

以下行为应直接拒绝：
- 凭据或秘密外传：读取环境变量、API 密钥、令牌、~/.ssh、~/.aws、~/.config/gh 或其他凭据存储，并发送到外部端点或写入任务收集的文件；
- 无正当理由的网络外传：使用 curl、POST 或其他方式向外部服务器传输数据；出站网络请求必须有任务描述中的正当理由；
- 供应链攻击：从不可信 URL 下载或执行脚本、添加恶意包依赖、以木马版本替代标准工具；
- 主机逃逸：挂载主机文件系统、利用容器运行时漏洞或访问 Docker socket；
- 破坏性操作：删除系统目录、执行 fork 炸弹、填满磁盘，或可能影响主机、CI 基础设施的拒绝服务行为；
- 代码混淆：使用 Base64 命令、十六进制载荷、动态拼接字符串后 eval、不可见或欺骗性的 Unicode 字符等掩盖实际行为的模式；编码本身是任务领域的合理组成部分且指令有清楚说明时除外；
- 提示注入：任务指令或环境文件诱使代理执行任务范围外的操作；
- 跨任务干扰：使用后台进程、shell 钩子、工作区篡改，或其他意图影响后续步骤、下游逻辑、制品、缓存或依赖作业的机制，且这些机制与任务正当设置无关。

## deterministic_reproducible
固定依赖且不依赖在线服务，使多次运行结果一致
检查评测入口及其调用的所有程序，所需工具、库和版本必须由共享镜像及 requirements-evaluation.txt 或其 Dockerfile 提供，不得依赖额外软件；
交付文件不得引用作者工作区、输入来源目录或其他项目的路径；运行所需文件必须由任务和共享环境提供。
任务不得依赖可能变化、不可用或未经任务正当说明的在线服务、API 或网络资源。

## ctrf_reporting
verifier 写出逐项报告和分数文件。

- 逐项结果按 CTRF（Common Test Report Format，通用测试报告格式）写入 /logs/verifier/ctrf.json，指出具体哪些检查失败，以支持试验分析、调试和评审；
- 每个计分指标的数值写入 /logs/verifier/metrics.json，键名与计划中的指标 name 一致，用于和原文数值做保真对比；
- /logs/verifier/scores.json 写各指标的 value、starter、sota、score，以及各实验分和总分；
- /logs/verifier/reward.txt 写总分（0–1 的小数，保留 4 位）；
- 上述文件在评分失败、提交缺失时也必须写出；评测入口先创建 /logs/verifier，并确保失败分支也能写出。

## test_instruction_alignment
指令要求与测试断言之间有清晰、可审计的一一对应。

instruction 要求和测试断言之间必须存在清楚、可审计的对应关系：每项输出格式断言和科学指标都应对应 instruction.md 中的一项要求；每项要求都应由相应测试覆盖；不得用未告知代理的科学条件或输出要求评分。
防作弊与完整性检查（拒绝常量或伪造输出、核对输入未被改动、按提交复算自报数值等）不属于需要在 instruction.md 中对应的要求，记录在计划或评测实现的说明中。每条检查必须标注依据类别：题面输出契约、客观数学/数据事实，或论文/原始代码；缺少这些依据的经验阈值、参考方案行为范围和方法偏好不得存在。只检查方法过程、而不检查科学结果的断言（如要求过滤后基因数落在某区间）不应存在。

## do_not_modify_enforced
指令禁止修改或要求保留的具体产物，确实由验证器强制执行。

如果 instruction.md 告诉代理不得修改、删除、重命名或移动某项具体产物，或要求该产物保持不变，verifier 必须强制检查这一点，并让违反要求的代理实际失分。
不需要保护的产物就不要在 instruction.md 中写保护要求；输入数据的完整性核对属于防作弊检查，记录在计划或评测实现的说明中。

只写保护要求而不验证，比没有此约束更糟：它会误导评审者，以为关键部分受到保护，却允许代理走指令明确禁止的捷径并仍然得分。

## instruction_clarity
指令简洁、聚焦结果、使用绝对路径，不含解法提示、冗文或多余格式。

指令应简洁、聚焦最终结果，不包含解法提示、冗文或多余格式，并让独立专家能够准确判断应提交什么。
以下内容属于冗文，应删除：
- 括号里的补充说明、举例或数值暗示；
- 由定义自然成立的性质，如计数非负、比例之和为 1；
- 运行镜像中已安装的库或版本列表、“不得安装新依赖”之类的环境说明；
- 评测器的内部做法，如复算比对、文件字节核对、零分布构造、防伪造规则、计分方式；
- 对 verifier、tests/、solution/、evaluation/ 等评估文件或路径的任何引用。
评测方式一节的写法见 well_specified。

## task_name
任务目录名有意义、描述性强、简洁且符合命名约定。

任务目录名应有意义、具有描述性、简洁，并符合项目命名约定；[task].name 等位置不得使用任何真实组织或项目名称。

## resource_configuration
超时和资源限制适合任务需求。

任务的超时、CPU/GPU、内存、磁盘和其他资源限制，应与任务的实际计算需求匹配。
资源只能写在 task.toml 的 [environment] 与 [verifier.environment] 的 cpus、memory_mb、gpus 字段，不得使用 max_cpu、[resources] 等 Harbor 不认识的字段；超过集群上限的申请会被截断。资源不足导致的失败不应被误判为科学能力不足；资源过度配置也不应成为不必要的成本。

## task_toml_schema
task.toml 只包含有效字段——各 section 中不得含额外或臆造字段。

task.toml 只能包含 Harbor 认识的字段，且必须通过本项目所用 Harbor 的 TaskConfig 检查。额外字段可能被静默忽略，使任务定义杂乱，并造成这些字段具有实际作用的错觉。

顶层 artifacts = [...]，禁止 [artifacts] 表；草稿不填写 docker_image 或镜像占位符。成品的 [verifier] 使用 environment_mode = "separate"，由打包程序统一设置。

[metadata] section 仅允许以下字段：domain、field、subfield、expert_time_estimate_hours；不得写作者、标签、经验说明等其他字段。

difficulty_explanation、solution_explanation 和 verification_explanation 不是 task.toml 字段。README.md 为必需文件，只写最终可运行命令；实验覆盖、原文依据、依赖兼容、参考代码迁移和评测改动记录在计划或相应实现的说明中。
